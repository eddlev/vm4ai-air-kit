# AIR and BinLing: source-routing integration

**Status:** Development direction for the next full-stack AIR candidate. This document does not change the currently promoted AIR Kit release, boot files, formal contracts or qualification status. BinLing-routed operation is not being announced as a released feature.

AIR is a self-contained, Apache-2.0 prompt-based framework. BinLing is a separately developed and licensed structured instruction and source-reference technology. AIR's governance is authoritative; optional routing helps locate applicable AIR source material.

## Target source-resolution configurations

| Configuration | Runtime dependency | Evidence boundary |
| --- | --- | --- |
| Native AIR direct source | AIR Foundation and applicable source packages | Direct source selection and validation |
| Offline compiled routing data | Version-matched, verified routing index plus complete native AIR sources | A stored resolution result, not an executed resolver receipt |
| Executed resolver (future) | Separately available, qualified BinLing resolver | Actual verified invocation and result; does not imply governance enforcement |

The public kit must not require private repository access, a BinLing account, a network service or the historical BinLing VM. The same applicable canonical AIR laws, floors, routes, mandatory prerequisites and approval boundaries apply in every supported configuration. A routing optimization cannot create execution authority.

A compiled index may become the public distribution's default source-selection aid only after full-stack coverage, integrity, applicable dependency equivalence, licensing and performance gates pass. Complete native direct-source routing must remain available.

## Integration contract requirements

The next candidate's build must pin the AIR source version and digest, route/dependency contract, capsule and index schema versions, generator identity and output commitments. Build all applicable routes from reconciled canonical source; preserve conditional applicability, source-body commitments, dependency closure, conflicts, unresolved prerequisites and nonbypass safeguards. An index must not substitute identifiers for actual law bodies.

An independent release verifier must compare compiled references and applicable dependencies against the direct-source contract. Evidence of a stored mapping or matching bytes is not evidence of historical resolver execution, model source utilization, semantic correctness, host authentication or independent enforcement.

When an index or resolver is unavailable, native routing may be used if authoritative source and mandatory dependencies can be established and affected state is revalidated. A conflicting, missing or mismatched mandatory source must not be bypassed through fallback. Unresolved mandatory requirements block the affected operation. Quoted capsule text is not a command or authorization.

These are integration requirements, not a new public capsule wire format or a claim that the implementation is complete. The versioned interface and release manifest will be reconciled with canonical source during implementation.

## Qualification

The full-stack candidate must demonstrate source completeness, direct/index equivalence for applicable routes, correct handling of missing and contradictory dependencies, verifiable provenance, safe fallback and useful performance. Field evidence and controlled comparisons must distinguish source availability, reference resolution, observed source utilization, behavioral adherence and independent enforcement. Existing limited pilots do not establish full-stack qualification.
